2. REQUIRED ROLE MODEL
==================================================

For this phase, the business permissions are deliberately simple.

There are exactly 3 user categories:

ADMIN
EMPLOYEE
MEMBER

French labels:

ADMIN
EMPLOYÉ
ADHÉRENT

The important rule is:

ADMIN and EMPLOYEE have the SAME operational management permissions
except for EMPLOYEE ACCOUNT MANAGEMENT.

ADMIN:
- manage members
- create members
- edit members
- deactivate/reactivate members
- reset member passwords
- manage subscriptions
- manage attendance
- manage payments where functionality exists
- manage courses
- manage course schedules
- manage course reservations
- book/cancel a class for a member
- view participant lists
- manage other normal gym operational modules
- AND manage EMPLOYEE accounts

EMPLOYEE:
- everything above EXCEPT employee management
- can create/manage MEMBER accounts
- can NEVER create an employee
- can NEVER edit an employee
- can NEVER disable an employee
- can NEVER reset an employee password
- can NEVER change somebody to EMPLOYEE or ADMIN
- cannot access employee-management API endpoints

MEMBER:
- can access only their own member area
- see their own subscription/data
- view classes
- reserve classes
- cancel their own class reservations
- see their own reservations
- edit allowed profile fields
- no administrative access

SECURITY MUST BE ENFORCED SERVER-SIDE.

Do not merely hide UI buttons.

An employee manually calling an employee-management API endpoint must receive
403 Forbidden.

4. AUTHENTICATION ARCHITECTURE
==================================================

There is currently no proper production authentication flow.

Implement real authentication in the .NET backend.

Use secure password hashing.

Prefer established ASP.NET Core mechanisms such as:
- PasswordHasher<TUser>
or
- ASP.NET Core Identity components where appropriate

Do NOT:
- store plaintext passwords
- encrypt reversible passwords
- use SHA256 alone
- store temporary passwords in database plaintext.

Implement a proper authenticated principal containing:
- UserId
- Email
- Role

Use a clean JWT/access-token authentication architecture suitable for the
existing React apps.

If you use refresh tokens, store them securely and make them revocable.

If using cookies, configure:
- HttpOnly
- Secure in production
- appropriate SameSite
- CORS credentials correctly.

Choose the cleanest architecture compatible with the current frontend/backend
structure.

6. TEMPORARY PASSWORD USER CREATION FLOW
==================================================

This is an important requirement.

Creation form:

When clicking:
"Créer le compte"

Backend must:

1. validate normalized email uniqueness
2. create the appropriate account/profile
3. generate a cryptographically secure temporary password
4. hash it immediately
5. save only the hash
6. set:
   MustChangePassword = true
7. return the temporary password ONLY in that successful creation response.

Frontend then opens a clear modal:

COMPTE CRÉÉ

XXXXXXXXXXXX

"Ce mot de passe ne sera plus affiché. L’utilisateur devra le modifier lors de
sa première connexion."

After the modal is closed, the temporary password must NOT be retrievable.

The database must NEVER contain that plaintext temporary password.
